<deviation_from_context>
**CONTEXT.md D-04 is necessary but not sufficient, and this plan deviates from it in ordering.**

D-04 states the deploy workflow change is the first commit. Research verified against the
GitHub REST API this session — and re-verified at planning time — that
`repos/ayhid/resume/pages` reports `"build_type": "legacy"` with
`"source": {"branch": "main", "path": "/"}`. GitHub's built-in `pages build and deployment`
workflow publishes the whole `main` root and never reads `deploy.yml`. The `_site/` allowlist
(D-05/D-06/D-07) therefore changes nothing until the publishing source is switched to GitHub
Actions, and `actions/configure-pages` cannot perform that switch — its `enablement` input
only creates a site when none exists, it never updates `build_type`.

So the first *action* of this phase is a repository-settings change, not a commit. D-04's
commit ordering is preserved: the deploy workflow change is still the first commit. The
settings switch precedes it, and precedes the first push, behind a blocking human gate.

This was not known at discuss time.
</deviation_from_context>

<research_decision>
**Open question resolved: yes, the deploy job chains on verify via `needs: verify`.**

D-08 specified a split by trigger, not a chain. The chain costs roughly twenty seconds per
deploy and means a manifest regression can never reach production. "The artifact was verified
before it shipped" is the entire point of OPS-01 and OPS-02. Chained.

Consequence to expect during execution: on a pull request the deploy job reports as *skipped*,
not failed, because `needs: verify` is satisfied while the `if:` is false. The pull request's
check run shows `verify` only.
</research_decision>
