<objective>
Prove the pull-request half of the pipeline empirically rather than by reading the workflow file:
open one throwaway pull request, watch verification run, watch nothing get published, then merge
it and watch publication happen. Close the phase with the human judgements no assertion can stand
in for.

Purpose: ROADMAP criterion 2 and OPS-01. Plans `01-01` through `01-04` proved the push path four
times over; the repository has never had a single `pull_request` workflow run in its history, so
the pull-request path is the one part of the pipeline that has only ever been reasoned about.
D-09 asks for exactly this experiment.

Output: one merged pull request, a recorded deployment-id invariance across its open window, and
the phase's end-of-phase human verification.
</objective>

<research_decision>
**The probe pull request is merged, not closed.**

D-09 allows either. Merging is chosen because it buys a second proof for free: OPS-04 states
deployment happens on merge to `main`, and every deploy in this phase so far has come from a
direct push. A merge commit exercises the same trigger through the path a reviewer would actually
use.

The probe change is therefore made worth keeping — a README line documenting the local staging
rehearsal — rather than a typo that would have to be reverted.

**Why this test is valid.** For a `pull_request` event GitHub runs the workflow file from the pull
request's merge commit, not from the base branch. Since the branch is cut from a `main` that
already carries the fixed workflow, the run exercises the fixed workflow. If the branch had been
cut before plan `01-01`, the test would have proved nothing.
</research_decision>
