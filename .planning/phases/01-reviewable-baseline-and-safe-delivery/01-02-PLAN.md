<research_decision>
**Open question resolved: the heading check ships as a warning in this phase, not a failure.**

Research assumption A5 assumed `index.html` carries exactly one `<h1>`. The pattern mapper
flagged it as false and it was re-confirmed at planning time: `grep -c '<h1' index.html` returns
**2** on the v2 working tree (lines 155 and 586) and **2** on the committed v1 file (lines 620 and
1103). One `<h1>` per `[data-lang-block]` is correct for this page's architecture — the inactive
locale tree is `hidden`.

So an unconditional single-`<h1>` assertion would be red on arrival, on both the file the first
pull request will check and the file that replaces it. A gate that is red before any change is a
gate nobody trusts. The heading rule is emitted as a warning that reports the total, the number of
language blocks and the per-block count. Phase 11 (A11Y-01) owns the decision to make it fail.

Two related facts were measured and drive the opposite call: `index.html` has **zero** duplicate
ids and **zero** tag-balance errors on both the v1 and the v2 file. Those two ship as hard
failures today.
</research_decision>

    - Any entry of `FORBIDDEN` present in the staged directory → one error naming it. Absent → no error.
    - `index.html` with balanced tags → no structural error.
    - `index.html` containing `<div><p></div>` → an error naming the mismatch and its line number.

    - `index.html` with an element left open at end of input → an error naming the tag and its opening line.
    - `index.html` with two elements sharing an `id` → an error naming the id and its occurrence count.
    - `index.html` with all-unique ids → no id error.
    - `sitemap.xml` that is well-formed XML → no error. Truncated or malformed → one error carrying the parser message.
    - `index.html` with two `[data-lang-block]` elements holding one `<h1>` each → no warning.
    - `index.html` with two `<h1>` and no language block → one `::warning::` reporting the counts, and the exit code is still 0.
    - A missing `index.html` → the required-entry error only; no attempt to parse it.

  <action>
    Create `.github/scripts/verify_site.py` following `01-RESEARCH.md` §Code Example 3, which is
    already written against this repository's manifest. The repository has no Python file and no
    test runner, so there is no in-repo style to copy and none is to be introduced — standard
    library only: `sys`, `pathlib`, `collections`, `html.parser.HTMLParser`,
    `xml.etree.ElementTree`. No package manifest, no install step, and no language-runtime setup
    action in the workflow — the interpreter is already on the runner image. This
    is the project's first automated check and it must not cost the repository its
    no-build-step, no-runtime-dependency property.

    Module constants: `REQUIRED` listing `index.html`, `CNAME`, `robots.txt`, `sitemap.xml`,
    `og-image.png` — the same five entries the staging script requires. `FORBIDDEN` listing
    `README.md`, `og-image.html`, `specs`, `.planning`, `.github`, `.claude`, `.playwright-mcp`
    and `_site`. `VOID` listing the HTML void elements so the tag stack does not try to close
    them. A module-level `errors` list collects problems.

    Subclass `HTMLParser` as `Checker`, constructed with `convert_charrefs=True`, holding a tag
    stack of pairs, a `collections.Counter` of ids, an `<h1>` counter, and per-language-block
    bookkeeping. In `handle_starttag`, count any `id` attribute, count `<h1>`, note the start of a
    `[data-lang-block]` element, and push non-void tags onto the stack with their line number from
    `getpos()`. In `handle_endtag`, ignore void tags, append a stray-close error when the stack is
    empty, append a mismatch error naming both the closing tag's line and the open tag's line when
    the top of the stack does not match, and pop otherwise. Add a header comment stating *why*
    every check is explicit — the parser has no strict mode and never raises, so its silence
    proves nothing — following the project's comment-the-why convention.

    `main(dest)` takes the staged directory as a `pathlib.Path`, appends an error for each missing
    `REQUIRED` entry and each present `FORBIDDEN` entry, then, when `index.html` exists, feeds it
    to a `Checker`, appends an unclosed-tag error for anything left on the stack, appends a
    duplicate-id error for every id counted more than once, and parses `sitemap.xml` with
    `xml.etree.ElementTree.parse`, converting a `ParseError` into an error carrying the parser
    message. Print each error as a `::error::` annotation, print the problem count, return 1 when
    the list is non-empty and 0 otherwise. Read the destination from `sys.argv[1]` defaulting to
    `_site`.

    **The heading rule is a warning in this phase, not a failure.** Measured at planning time:
    both the committed page and the incoming rewrite carry two `<h1>` elements, so a hard
    single-heading assertion would fail on markup this phase is forbidden from editing. Emit a
    `::warning::` reporting the total `<h1>` count, the number of `[data-lang-block]` elements and
    the count inside each, when the document does not expose exactly one heading per language
    block, or exactly one document-wide where there are no language blocks. The warning must not
    contribute to the error list and must not change the exit code. Add a comment recording that
    Phase 11 owns A11Y-01 and inherits the decision to make it fail.

    **Prove the checker actually catches things before trusting it.** In a temporary directory
    outside the repository, build a staged tree, confirm a clean run exits 0, then run each
    negative case from the `<behavior>` block — a removed required entry, a planted forbidden
    entry, a mismatched tag, a stray close, an unclosed element, a duplicated id, a truncated
    sitemap — and confirm each exits 1 with the expected annotation. A checker that has never been
    shown to fail is not a checker. Do not commit any fixture; the temporary directory is
    scratch.

    **Wire it in.** Add a `Verify artifact contents` step running
    `python3 .github/scripts/verify_site.py _site` immediately after the existing
    `Stage production artifact` step, in **both** the `verify` job and the `deploy` job. Both jobs
    must run the identical pair of commands so the pull-request check is a real rehearsal of the
    publish rather than an approximation. Preserve the file's conventions: two-space indent, a
    blank line between step blocks, a `- name:` on every step, no trailing whitespace, terminating
    newline. Do not change the action pins, the triggers, the permissions, the concurrency groups
    or the `if:` gate.

    Finally, run the same pair of commands locally against the working tree —
    `bash .github/scripts/stage-site.sh _site && python3 .github/scripts/verify_site.py _site` —
    and confirm it exits 0 against the currently committed page. That page is what the next push's
    verify job will check, so a red result here means the gate is red on arrival and must be fixed
    before it is committed.
